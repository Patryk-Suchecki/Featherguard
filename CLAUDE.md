# Featherguard

Original turn-based mobile game: a squad of birds fights lizards in side view, low-poly 3D. Between battles the run is driven by gambling rewards (slot machine, double or nothing, card picks, shop, cursed chest). Unity 6000.6.2f1, URP, uGUI built from code, Input System, landscape mobile.

Two people develop this repo, each with their own Claude. These rules are shared; follow them even when a request seems to imply otherwise, and say so if a request conflicts with them.

Never recreate an existing game's names, characters, art or music. Everything stays original.

## Architecture

Assemblies: `Featherguard` (Assets/Scripts), `Featherguard.Editor` (Assets/Editor), `Featherguard.Tests.EditMode` (Assets/Tests/EditMode). Namespaces are per module, not per folder, because `[SerializeReference]` data stores full type names. Never rename a namespace or a serialized class without `[MovedFrom]`.

| Module | Path | Role |
|---|---|---|
| Core | Scripts/Core | `IRandomSource`, `WeightedRandom`, `SubclassSelector` |
| Battle model | Scripts/Battle/Definitions, Scripts/Battle/Model | Pure C# battle: `BattleModel.Start()/Act()` resolve synchronously and return `BattleEvent` lists. No GameObjects, coroutines or waits. |
| Battle presentation | Scripts/Battle/Presentation | `BattlePresenter` replays events through `UnitView`s, `PlayerCommands` handles input, `BattleController` glues model and presenter. |
| Run | Scripts/Run | `RunSession`, party, wallet, upgrade deck; `Run/Rewards` holds reward logic (slots, gamble, shop, card draft, path). |
| Meta | Scripts/Meta | Perks and feathers, `ISaveStore` (JSON file in `Application.persistentDataPath`). |
| Feel | Scripts/Feel | Audio, VFX, hitstop, camera shake, `GameClock` pause. |
| UI | Scripts/UI | HUD, reward screens and camp, all built in code. UI only displays and forwards input; it never contains game rules. |
| Game | Scripts/Game | `GameBootstrap` composition root, `GameConfig`. |

Layer rules:
- Model code never references Presentation, UI, `MonoBehaviour`, `Transform` or `WaitForSeconds`.
- New gameplay goes into the model plus a new `BattleEvent` if the presenter must show it. Reward or economy logic goes into `Run/Rewards`, not into UI steps.
- Extend behaviour through the existing strategies (`AbilityEffect`, `AbilityDelivery`, `SlotReward`, `PerkEffect`, `IEnemyBrain`) instead of adding switch statements.

## Data and balance

All tuning lives in ScriptableObjects under `Assets/Data`:
- Units, Abilities, Statuses, Encounters, Upgrades, Perks.
- Single assets: `BattleRules`, `BattlePresentation`, `Economy`, `SlotMachine`, `Run`, `Meta`, `GameConfig`.

Change balance by editing those assets, not code.

Default content is seeded from `Assets/Editor/Setup/*Catalog.cs`:
- **Featherguard > Rebuild Battle Scene** creates missing assets and refreshes art links without overwriting edited values. It also regenerates `Assets/Scenes/Battle.unity` and `Assets/Settings/BattlePostFX.asset`.
- **Featherguard > Reset Data To Defaults** overwrites all data with catalog values. Only run it on purpose.
- When you add content, add it to the catalog too, so a fresh checkout can rebuild it.

`docs/GAME_DESIGN.md` describes what is in the game. Update it in the same PR whenever you change content or rules.

## Generated art and audio

- **Characters and environment:** generated by Blender 5.x scripts in `Art/Blender`, run headless:
  - `blender -b -P Art/Blender/build_characters.py`
  - `blender -b -P Art/Blender/build_environment.py`
  - `blender -b -P Art/Blender/render_portraits.py`

  They write `.fbx` to `Assets/Art/Characters`, `Assets/Art/Environment` and `Assets/Art/UI/Portraits`, plus `.blend` files to `Art/Blender/Characters`.
- **Icons and sound effects:** generated by `IconFactory` and `SfxSynth` during Rebuild. `GeneratedFiles.Write` skips unchanged files and refuses to overwrite a read-only (unlocked) file.
- **Regenerating assets is a separate PR.** Lock the binaries you will change first (`git lfs lock <path>`), then unlock after merge.

## Tests

- **EditMode tests** live in `Assets/Tests/EditMode/{Battle,Run,Meta,Support}`. They cover the battle model (full headless simulations), economy, rewards and meta.
- **Running them** (use whichever is available):
  - In the editor: Window → General → Test Runner → EditMode → Run All.
  - With the optional Unity CLI connected to an open editor: `unity command test run --mode EditMode --filter Featherguard`.
  - Without an open editor (the project must be closed in Unity): `"<Unity.exe>" -batchmode -projectPath . -runTests -testPlatform EditMode -testResults Temp/results.xml`.
- **Before every push:** run the tests. Add or update tests for any rule or economy change. Prefer testing the model directly with `FakeRandom`.
- If you cannot run the tests or the game yourself, ask the person you work with to run them and report back. Never claim tests passed or something works without seeing it.

## Code style

`.editorconfig` enforces formatting; follow the existing code when in doubt.

- C# 9 as supported by Unity 6. Block-scoped `namespace Featherguard.<Module>` (not file-scoped), 4-space indent, braces on their own lines.
- `using` directives at the top, `System` first, then `Featherguard`, then `UnityEngine`/`UnityEditor`.
- One main type per file, file named after it. Small closely related types may share a file (event classes, strategy variants such as `DamageEffect`/`HealEffect`, small data structs).
- Naming: types, methods, properties, events, constants and `static readonly` fields in `PascalCase`; other fields, locals and parameters in `camelCase`; interfaces start with `I`. No `_` prefix and no Hungarian notation.
- Omit the default `private` modifier on fields and methods. Mark fields `readonly` when possible.
- Plain C# classes are `sealed` unless designed for inheritance. Strategies (`AbilityEffect`, `SlotReward`, ...) are `[Serializable]` abstract base classes with `sealed` implementations.
- ScriptableObject data uses public `camelCase` fields with `[Tooltip]`, `[Range]`, `[Min]` and `[Header]` where they help the inspector.
- MonoBehaviours use `[SerializeField]` private fields, never public fields, for scene references.
- Use `var` when the type is obvious, expression-bodied members for one-liners, target-typed `new()`.
- No `#region`, no XML doc comments, no commented-out code, no `Debug.Log` left in gameplay code.
- Logic is synchronous and testable; coroutines and `WaitForSeconds` live only in presentation and UI.
- Randomness always goes through `IRandomSource` so tests can control it.

## Working as Claude in this repo

- Each developer has their own Claude session; `CLAUDE.md` and `.claude/settings.json` are the only shared instructions. Personal memory is not shared, so anything both sessions must follow belongs here.
- Start every change from an issue. If there is none, propose one and create it with `gh issue create` using the matching template once your developer agrees.
- Branch from an up-to-date `main`, keep the PR small, run the tests, push, and open the PR with `gh pr create` following `.github/pull_request_template.md`.
- Never do these without your developer explicitly asking in this conversation:
  - approve or merge a pull request, or close someone else's issue or PR;
  - push to `main`, force-push, rewrite history or delete branches you did not create;
  - change GitHub repository settings, rulesets, collaborators or labels;
  - run **Reset Data To Defaults**, regenerate art or audio, or change `ProjectSettings`, `Packages/manifest.json` or the Unity version.
- Before ending a task, check `git status`: commit only files that belong to the task and discard Rebuild noise.
- Write in English in the repo; reply to your developer in whatever language they use.

## Conventions

- Everything is in English: code, identifiers, file names, in-game text, data assets, docs, commits, branches and PRs.
- Avoid unnecessary comments; names should explain the code.
- Small, focused classes; constructor injection; configuration in ScriptableObjects; no singletons beyond `FeedbackHub.Instance` and `RunSession.Current`.
- Every piece of work starts from a GitHub issue. One issue → one branch → one small PR. Never push directly to `main`.
- Branch names: `<type>/<issue>-<short-task>`, where type is `feature`, `fix`, `balance`, `art` or `chore`, for example `feature/12-slot-machine-sounds` or `fix/15-double-kill-gold`.
- Commit messages: `#<issue> <what this commit does>`, one short imperative line (max ~60 characters) naming the exact task, for example `#12 Add jackpot sound to slot machine`. No body unless something is surprising.
- PR title: `#<issue> <task>`; the description starts with `Closes #<issue>`. PRs are squash-merged after one approval from the other developer.
- Issue labels: `gameplay`, `art`, `audio`, `UI`, `bug`, `balance`. Docs and tooling work (`chore/` branches) needs no label.
- Never add AI attribution: no `Co-Authored-By` trailers, no "Generated with Claude Code" lines, no mention of AI tools in commits, branches or PRs. `.claude/settings.json` disables it; keep it that way.

## Unity pitfalls

- Everyone uses Unity **6000.6.2f1** exactly. Never upgrade the editor or packages in a feature PR.
- Never hand-edit `.unity`, `.prefab` or `.asset` YAML while an editor has the project open; Unity overwrites it. Prefer editing through scripts or the inspector.
- Only one person changes `Battle.unity` at a time. Rebuild regenerates it, so discard scene, post-FX and ProjectSettings noise from a Rebuild (`git restore`) unless the PR is about them.
- Always commit `.meta` files together with their assets; moving a script or asset must move its `.meta` (use `git mv`) to keep GUIDs.
- Binaries (`fbx`, `blend`, `png`, `wav`, `ogg`) are in Git LFS and lockable: lock before editing and unlock after merging.
- Set up Unity Smart Merge once per clone (see `docs/CONTRIBUTING.md`).
